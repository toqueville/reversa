# Bug Record (Reversa Bugs)

> Generated by Reversa on {{DATA}}. This file is the bug record contract for this project.
> Source of truth: each `<context>/bugs/<ID>/bug.md`. Everything in `generated/` is a regenerable projection.

## Project configuration

```yaml
closure_policy: {{CLOSURE_POLICY}}   # local-software | package | production-service
control_mode: gated                  # supervised | gated | autonomous
```

- `closure_policy` defines what "resolved" requires:
  - `local-software`: regression tests passing + spec verdict
  - `package`: above + merge + corrected version published (+ required backports)
  - `production-service`: above + delivery + observation window with no recurrence
- `control_mode: gated` (default): reading, isolated reproduction, and diagnosis flow without approval;
  mandatory gate to apply tests, apply change set, alter effective spec, use external
  harness with project access, and any destructive operation.

## Structure

Bugs are grouped by **context** (feature, module, or use case, in the reporter's language). Each context is an aggregating folder with EVERYTHING from that area: bugs, inspections, and views. The folder is born on demand, when the first problem in that area is reported; nothing is created empty.

```text
_reversa_bugs/
├── README.md                    this contract
├── taxonomy.yaml                controlled vocabulary of area/module/feature
└── <context>/                   e.g., credit-system/, shopping-cart/
    ├── bugs/BUG-<date>-<suffix>-<slug>/   unique bug folder (IMMUTABLE address, never moves)
    │   ├── bug.md               canonical record
    │   ├── evidence/  ├── debate/  └── fix/
    ├── inspections/<scan>/      fine-tooth comb reports for the context
    └── generated/               context views, regenerated by /reversa-debugger-graph
```

## Lifecycle

`status`: `open` → `active` → `resolved`. `phase` details the step within `active`
(mitigating, reproducing, diagnosing, testing, patching, delivering, observing, awaiting-human).
Blocking is a condition (`blocking:`), never a status. Every closure has a `resolution_kind`.

**Completion lock:** upon satisfying the closure policy, the bug receives `DONE.md` in its folder and becomes
READ-ONLY for all agents. Reopening: consciously remove the lock, or register a
new bug with `regression-of`. The list of locked bugs appears in the context's `graph.html` (derived
view, no manual editing).

## Traceability rule

Every bug MUST identify:

1. The spec section that defines the expected behavior (effective spec = original + active addenda).
   Without a spec, the bug carries the `spec-gap` label and the gap is addressed before resolution.
2. The affected code (where it appears) and, after investigation, the root cause (where it originated), with
   epistemic state and evidence.
3. The reproduction and regression tests.

A bug CANNOT be `resolved: fixed` with empty `traceability.specs`, `root_cause` (confirmed), or
`regression_tests`.

## Agent protocol

1. Recording (`/reversa-debugger`) NEVER fixes. Fixing (`/reversa-debugger-fix`) follows two approval
   gates with diffs (tests that fail; change set that makes the tests pass).
2. The original spec is NEVER edited. Spec changes become versioned and immutable addenda in
   `<output_folder>/addenda/bug-<ID>-vNNN.md`, with the human decision recorded.
3. Code diff and spec diff/addendum are recorded TOGETHER in the bug's Resolution.
4. Bugs with `visibility: restricted` are excluded from views and nothing exploitable goes to external harnesses.
5. Relations and root cause have epistemic state: a hypothesis is not a fact.

## Conventions

- Canonical ID: `BUG-<YYYYMMDD>-<suffix>` (merge-safe). `display_number` is a human alias.
- References always by ID; views resolve the path.
- Evidence in `evidence/`, never giant logs inside the Markdown.
- Full schema: see `bug-schema` in the Reversa documentation (agents/reversa-debugger/references/).
