# reversa-spec-sdd, Spec-Driven Development in Reversa

This skill drives the complete SDD process within the Code New Project Agents pipeline: **decompose → write → evaluate → iterate** until each spec is ready for the forward cycle.

The skill is a vendored version of the global `sdd-spec`, adapted for the Reversa context: reads `prd.md` as the primary source, writes to `_reversa_sdd/sdd/`, marks everything with the 🟡 seal, and ends with a handoff to `/reversa-forward`.

## Why SDD?

Specs written before code save time because:

- They make ambiguities visible before they become bugs
- They align expectations between requesters and implementers
- They serve as a permanent reference for tests, reviews, and onboarding
- They allow LLMs to implement with much greater precision

The methodology here is **Pragmatic RFC plus LLM-First**: structured like an RFC (Problem / Goals / Design / Edge Cases), but optimized to be consumed by both humans and AI agents.

## Before starting

1. Read `.reversa/state.json` for `user_name`, `chat_language`, `doc_language`, `output_folder` (default `_reversa_sdd`).
2. Verify precondition: **`<output_folder>/prd.md` must exist**. If absent, terminate with a clear message:
   > "I could not find `<output_folder>/prd.md`. Run `/reversa-drafter` first, or invoke `/reversa-new` to drive the complete pipeline."
3. Ensure the folder `<output_folder>/sdd/` exists. Create it if absent.

## Default output path

Each generated spec goes to:

```
<output_folder>/sdd/<component-kebab-case>.md
```

For example: `_reversa_sdd/sdd/user-authentication.md`, `_reversa_sdd/sdd/payment-checkout.md`.

The component is decomposed from the `prd.md` in the first phase.

## Mandatory 🟡 seal

All items in specs generated by `reversa-spec-sdd` must use the **🟡 PLANNED** seal (variant of 🟡 INFERRED used in other Reversa contexts). The 🟢 CONFIRMED seal is reserved for facts extracted from existing code by the Discovery Team, a rule inherited to avoid confusion between "legacy fact" and "forward hypothesis".

Each requirement, behavior, edge case, and acceptance criterion in the specs must begin with 🟡.

## Workflow

### Phase 0, Decomposition into components

Read `<output_folder>/prd.md` in full. From the "Scope", "Target Personas", and "Acceptance Criteria" sections, propose a decomposition of the product into logical components. Each component should represent a cohesive unit that will become an individual SDD spec.

Present the decomposition to the user:

> "Based on the PRD, I identified these logical components:
>
>   1. **<component 1>**: <one-sentence description>
>   2. **<component 2>**: <one-sentence description>
>   3. **<component N>**: ...
>
> Do you agree with this decomposition? Do you want to add, remove, or rename any?"

Wait for a response. Iterate until confirmed (maximum 2 adjustments). For each confirmed component, normalize the name to kebab-case ASCII.

### Phase 1, Interview per component (optional)

For each component, decide whether the information in `prd.md` is sufficient:

- **Sufficient:** go directly to Phase 2.
- **Insufficient:** ask at most 3 focused questions, covering the points below that are missing:
  1. **The specific problem of that component:** "What is the role of `<component>` in the product?"
  2. **Success:** "How will you know this component worked? What can the user accomplish?"
  3. **Scope:** "What is explicitly OUT OF SCOPE for this component?"
  4. **Edge cases:** "Can you already anticipate difficult cases or error situations in this component?"

Limit: 3 questions per component, choosing the most critical ones.

### Phase 2, Write the spec

Use the template in `references/spec_template.md` as a base. Fill in **all** sections:

- **Functional requirements:** format `RF-01`, `RF-02`. Each one independently testable. Mandatory 🟡 seal.
- **Behaviors:** describe what happens, not how to implement. The spec defines the **what**, not the **how**.
- **Zero ambiguity:** if uncertain, mark with `⚠️ OPEN:` and add to the Open Questions list.
- **LLM-readiness:** write as if a developer or LLM would implement without asking anything.
- **🟡 seal on all spec items**, including FRs, edge cases, criteria.

Use `<doc_language>` for spec content.

### Phase 3, Automatic quality evaluation

After writing each spec, run the scorer.

**Python detection:** try `python --version` or `python3 --version` via shell.

- **If Python is available:**

  ```
  python scripts/spec_scorer.py --spec <output_folder>/sdd/<component>.md
  ```

  Use the literal output of the script.

- **If Python is not available (manual mode):** apply the procedure from the "Scoring in engines without Python" section below.

The scoring returns:

- **Total score** (0 to 100) with breakdown by dimension
- **Critical gaps** that need resolution
- **Suggestions** ordered by impact

Evaluated dimensions (see `references/evaluation_rubric.md` for details):

| Dimension | Weight | What it evaluates |
|---|---|---|
| Completeness | 30% | All sections filled, requirements covered |
| Testability | 25% | Verifiable requirements, clear acceptance criteria |
| Clarity | 20% | Absence of ambiguities, precise language |
| Scope | 15% | Non-goals defined, clear boundaries |
| Edge Cases | 10% | Error cases and system limits covered |

### Phase 4, Iteration

Based on the score:

1. Score **≥ 80**: spec is ready. Persist and move to the next component.
2. Score **60 to 79**: fix the obvious gaps automatically, then confirm with the user if anything critical is missing. Re-run scoring.
3. Score **< 60**: return to Phase 1 with questions focused on the gaps. Re-run scoring.

Limit: **3 iterations per component**. After 3 attempts, persist with the current score and add a `## Quality Pending Items` section to the file.

Show the delta at each iteration: "went from 54 to 71, 2 critical gaps remaining".

### Phase 5, Persistence and handoff

For each completed component:

1. Write `<output_folder>/sdd/<component-kebab-case>.md` with atomic write (tempfile plus rename), UTF-8 without BOM.
2. Include the **evaluation report** at the end of the file (score + gaps + suggestions).
3. If the file already exists, ask the user whether to overwrite.

After generating **all** specs, display a consolidated report:

> "`<user_name>`, SDD generation complete. Specs created in `<output_folder>/sdd/`:
>
> | Component | Path | Score | Iterations |
> |---|---|---|---|
> | <comp1> | <output_folder>/sdd/<comp1>.md | 87 | 1 |
> | <comp2> | <output_folder>/sdd/<comp2>.md | 73 | 2 |
> | <comp3> | <output_folder>/sdd/<comp3>.md | 68 | 3 (with pending items) |
>
> All items marked with 🟡 seal (planned).
>
> Next step: run `/reversa-forward`, which will consume these specs and start the evolution cycle toward code.
>
> Type **CONTINUE** to start `/reversa-forward`, or pause here."

Never proceed automatically.

## Scoring in engines without Python

When `python --version` and `python3 --version` fail, activate manual mode:

1. **Read `references/evaluation_rubric.md`** for the criteria of each dimension.
2. For each of the 5 dimensions, mentally evaluate the spec and assign a score from 0 to 100, justifying in 1 to 2 sentences:

   - **Completeness (30%):** are all 9 mandatory sections filled? Do FRs cover the declared scope?
   - **Testability (25%):** are FRs independently verifiable? Do acceptance criteria have Given/When/Then format or equivalent?
   - **Clarity (20%):** are there vague phrases (intuitive, fast, easy)? Are there contradictions?
   - **Scope (15%):** are non-goals explicitly declared? Clear boundaries?
   - **Edge cases (10%):** at least 3 error/boundary cases covered?

3. **Calculate the weighted score:**

   ```
   score = (Completeness * 0.30) + (Testability * 0.25) + (Clarity * 0.20)
         + (Scope * 0.15) + (Edge Cases * 0.10)
   ```

4. **List the gaps** in order of criticality (blockers, important, improvements).

5. **Render the output** in the same format as the script:

   ```
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   TOTAL SCORE: <NN>/100
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   Breakdown:
     Completeness:  <NN>/100 (weight 30%)
     Testability:   <NN>/100 (weight 25%)
     Clarity:       <NN>/100 (weight 20%)
     Scope:         <NN>/100 (weight 15%)
     Edge Cases:    <NN>/100 (weight 10%)

   Critical gaps:
     - <gap 1>
     - <gap 2>

   Suggestions (by impact):
     1. <suggestion>
     2. <suggestion>
   ```

The result in manual mode should be equivalent to the script's output for the same spec.

## Mode: existing spec evaluation

If the user invokes `/reversa-spec-sdd` outside the `/reversa-new` pipeline, with an already-written spec for evaluation:

1. Ask for the file path.
2. Run scoring (script or manual).
3. Present the score with detailed analysis per dimension.
4. List gaps in order of criticality.
5. Ask whether the user wants you to fix the identified issues.

This mode does not require `prd.md` and does not enter the pipeline. It is a standalone utility inherited from the original skill.

## Signs of a bad spec (avoid)

- Requirements that cannot be tested ("the system should be intuitive")
- Scope section absent or vague ("we'll see what makes sense")
- Mixing technical implementation design with expected behavior
- Contradictory requirements not flagged
- No acceptance criteria defined
- Error edge cases completely absent

## Signs of a good spec (aim for)

- Any developer can implement without asking questions
- Any QA can write tests from it
- The non-goals are as clear as the goals
- Error cases have defined behavior
- Each requirement has a unique traceable ID
