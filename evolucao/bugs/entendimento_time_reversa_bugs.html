Proposal for Sandeco's approval. No implementation was done: this document records what was understood.

Sources: evolucao/bugs/conversa_reversa_bugs_rastreabilidade.md and evolucao/bugs/parecer_reversa_bugs_pratica_diaria_para_claude.md

1.Executive summary

The Reversa Bugs Team adds to Reversa a causal defect memory: a bug registry in Markdown, within the user's project, designed to be read and maintained by LLM agents on any engine (Claude Code, Codex, Cursor, Gemini CLI). Each bug is a file with YAML front matter, traceable to the specs extracted by Reversa (_reversa_sdd/), to the code and to the tests. The team has 5 commands and a central rule inherited from the original conversation: documenting a bug and fixing a bug are brutally separate acts.

CommandRoleWrites to
/reversa-bugRegisters and traces a reported bug. Never fixes._reversa_bugs/BUG-XXX-slug/ (the bug's unique folder)
/reversa-bug-fixReproduces, finds root cause, creates regression test, fixes with approved diff and gives the spec verdict.code (with approval), the bug's folder (fix/), _reversa_sdd/addenda/
/reversa-bug-debateMulti-agent debate (fixed epochs + isolated judge) on the fix strategy. Always opt-in.debate/ within the bug's folder
/reversa-depth-inspectionDeep inspection of a problematic feature with specialized lenses. Diagnoses only._reversa_bugs/inspections/ + new bug folders

2.Origin and decisions already made

The design originates from the Sandeco x ChatGPT conversation (bugs as traceability nodes SPEC ↔ CODE ↔ TEST ↔ BUG) and was refined in this session with the following decisions by Sandeco:

Locked decisions
  • 5 commands: /reversa-bug, /reversa-bug-fix, /reversa-depth-inspection, /reversa-bug-graph, /reversa-bug-debate.
  • Canonical registry in _reversa_bugs/ at the root, following the pattern of Reversa folders and the non-destructive directive.
  • Deep inspection only diagnoses: each finding becomes a BUG-XXX.md; the fix is always a separate, subsequent act.
  • Debate is explicit opt-in: Reversa announces the option exists, explains it takes time (N agents x R rounds + 1 judge) and only runs if the user accepts.
  • Multi-harness debaters (Codex, OpenCode, Gemini CLI): Reversa announces when it detects other installed harnesses, but only includes them in the debate if the user accepts or explicitly requests it.
  • Diff and handoff: every fix shows the diff before applying; every step ends with a manual handoff ("Type CONTINUE"). Nothing advances on its own.
  • Spec verdict: every fix checks whether the original spec of the buggy code should be versioned and changed, and the diffs (code and spec) are recorded together in the bug.
  • Single folder per bug: all documents of a bug (registry, evidence, debate, fix diffs) live in a single folder BUG-XXX-slug/. Nothing from that bug is scattered across global folders. (The physical status layout has two variants, see section 4; the Codex recommendation is flat folder.)
  • BUG ↔ SPEC traceability matrix: explicit cross-reference, in both directions, between the bug folder and the spec section in _reversa_sdd/ that defines the behavior. The spec side also records the bugs that affect it (via a generated mirror file, since the original spec is never edited).
  • Delivery: consolidated spec in specs/reversa-bugs/ + implementation + installer registration + bump to 1.2.52. Only after authorization.
  • Daily practice assessment incorporated (2026-07-15): the bug stops modeling only "fix code" and starts modeling the full defect lifecycle. Complete triage in section 13: what was adopted in full, what was adopted in simplified form, what was deferred.

3.Reversa principles inherited by the team

  • Non-destructive: no pre-existing project artifact is deleted or overwritten. The team only creates files in _reversa_bugs/ and addenda in _reversa_sdd/addenda/. The controlled exception is the act of fixing code in /reversa-bug-fix, which follows the precedent of /reversa-coding: only with diff displayed and explicit approval.
  • Multi-engine: nothing depends on an exclusive feature of a harness. Where there are sub-agents (debate, deep inspection), there is a documented sequential fallback.
  • Manual handoff: each agent finishes by suggesting the next step and waiting for "CONTINUE".
  • Standard Reversa menus: options with label + description + final open "Other" option.
  • Vendor-in: the multi-agent debate loop is copied and adapted into Reversa, without depending on global skills from Sandeco's machine.
  • Source of truth: the BUG-XXX.md file is the truth. Index, matrix and graph are regenerable views.

4.The _reversa_bugs/ folder: one folder per bug

Each bug is a folder, and everything about that bug lives inside it. No artifact of a bug resides in a global folder: looking at BUG-007-desconto-duplicado/ you see the registry, the evidence, the debate (if any) and the fix, without hunting for anything.

_reversa_bugs/
├── README.md            registry rules, lifecycle, project closure policy (generated on 1st run)
├── taxonomy.yaml        controlled vocabulary of area/module/feature (seeded from _reversa_sdd/ extraction)
├── bugs/
│   ├── BUG-20260715-A7K3-desconto-duplicado/   ← the bug's unique folder
│   │   ├── bug.md       canonical registry (YAML front matter with status + phase, source of truth)
│   │   ├── evidence/    logs, screenshots, dumps, reproduction capsule (never huge logs in Markdown)
│   │   ├── debate/      if opened: rounds, convergence, final-answer.md
│   │   └── fix/         change set: code diffs, spec, config, repair scripts, verification.md
│   └── BUG-20260716-P9M2-.../ ...
├── inspections/<feature>/  deep inspection reports (point to bugs by ID)
└── generated/           regenerable views, never manually edited
    ├── index.md         summary and tables by status/phase + current path of each bug
    ├── catalog.jsonl    compact catalog (normalized front matter) for two-stage search
    ├── matrix.md        BUG x BUG relationships (sparse edge list)
    ├── graph.md         relationship graph + clusters + impact score
    └── spec-matrix.md   BUG ↔ SPEC traceability matrix (section 6.6)

Merge-safe identity: the canonical ID is BUG-<date>-<suffix> (e.g.: BUG-20260715-A7K3), globally unique even with two harnesses registering bugs simultaneously in different worktrees (Claude in one, Codex in another). An optional human display_number (42) lives in the front matter for day-to-day conversation.

Where status lives: decision closed by dual review

The two independent assessments (Codex, section 12.7; daily practice, section 13) converged: the bug folder never moves; status and phase live in the front matter and the views materialize the state-based views. Keeping folder and field saying the same thing is redundancy that requires divergence validation. The table below remains as a record of the comparison:

A. Status folders (original conversation)B. Flat folder + status in front matter (firm Codex recommendation)
Layoutopen/BUG-007/, active/BUG-007/, resolved/BUG-007/: the entire bug folder moves on each transition._reversa_bugs/BUG-007/ fixed forever; status: lives only in bug.md; index.md presents the views by status.
ProsStatus visible in the file explorer, without opening anything.Immutable physical address: links never break, no rename conflict between git branches, tools find the bug in one place only.
ConsEvery external link breaks on each transition; two branches moving the same bug generate rename/rename conflict; searching for an ID requires looking in 3 places.Knowing the status requires opening bug.md or index.md.

As the Codex put it: "the organization by state is a projection, not part of the bug's identity." References between documents always use the ID, never the path.

Ontology: 3 statuses + phase

status continues with only 3 values (open, active, resolved), and a separate phase field records the lifecycle stage within active (e.g.: mitigating, reproducing, diagnosing, patching, observing, awaiting-human). Blocking is a condition, not a state: structured field blocking: (by another bug or external cause) with derived is_blocked. A bug only becomes resolved when the project's closure policy is satisfied (section 13): local library closes with regression tests passing; production service only closes after deployment and observation without recurrence. And every closure carries a resolution_kind (fixed, duplicate, invalid, cannot-reproduce, spec-only, instrumentation-required).

taxonomy.yaml

Prevents agents from inventing inconsistent names. The area, module and feature fields of every bug MUST use values from this catalog. If nothing fits, the agent uses unclassified and proposes the new term in Agent Notes. On the first run, the catalog is seeded from the extraction modules (_reversa_sdd/architecture.md).

5.Anatomy of a bug (complete example)

Example in a legacy sales system whose Reversa extraction recorded the rule "maximum 10% discount per order" in _reversa_sdd/domain.md:

File: _reversa_bugs/bugs/BUG-20260715-A7K3-desconto-duplicado/bug.md
---
schema_version: 1
id: BUG-20260715-A7K3        # canonical identity, merge-safe
display_number: 7            # human alias: "BUG-007" in conversation
title: Desconto aplicado duas vezes no fechamento do pedido
status: open                 # open | active | resolved (the folder never carries the status)
phase: triaging              # lifecycle stage
severity: high
priority: P1
created: 2026-07-15
updated: 2026-07-15

origin:
  type: manual-report        # or github-issue, ci-failure, telemetry, inspection...

area: vendas
module: checkout
feature: desconto

labels:
  - financeiro

visibility: normal           # normal | internal | restricted (security flow)

reproduction:
  classification: deterministic   # deterministic | intermittent | environment-dependent | not-reproduced
  rate: 10/10

blocking: []                 # conditions that block the bug (another bug or external cause)

relationships:
  - bug: BUG-20260701-Q2R8   # canonical edge, recorded once; inverse is derived
    type: related-to
    state: proposed          # proposed | supported | confirmed | rejected

traceability:
  specs:
    - _reversa_sdd/domain.md#regras-de-desconto
  affected_code:
    - src/checkout/fechamento.py
  root_cause: null           # filled by the fix, with epistemological state and evidence
  reproduction_tests: []     # proves the reported defect appears
  regression_tests: []       # protects behavior that must not break again

spec_verdict: null           # filled by the fix, with human approval
change_set: []               # typed corrective changes (test, code, config, data-repair, spec...)

closure:
  policy: local-software     # detected on the team's 1st run in the project
  satisfied: false
resolution_kind: null        # fixed | duplicate | invalid | cannot-reproduce | spec-only | instrumentation-required
---

# Desconto aplicado duas vezes no fechamento do pedido

## Summary
Orders with a coupon have the discount applied in the cart and again at checkout,
resulting in an effective discount above the 10% cap defined in the spec.

## Expected Behavior
Per `_reversa_sdd/domain.md#regras-de-desconto`: maximum 10% discount
per order, applied only once.

## Actual Behavior
An R$ 100 order with a 10% coupon closes at R$ 81 (19% discount).

## Steps to Reproduce
1. Add an R$ 100 item to the cart
2. Apply coupon DEZ10
3. Close the order
4. Check the total: R$ 81 instead of R$ 90

## Evidence
- Log: evidence/fechamento.log          (paths relative to the bug's folder)
- Screenshot: evidence/total-errado.png

## Suspected Area
`src/checkout/fechamento.py`, function `aplicar_ajustes()`.

## Acceptance Criteria
- Discount applied exactly once, 10% cap respected
- Regression test covering order with coupon
- Existing tests continue passing

## Agent Notes
Do not alter the shipping calculation during the fix.
Why the front matter matters
It transforms the registry into a database navigable by grep. The user can ask "fix all open P1s" or "analyze bugs in the checkout module" and the agent filters by priority: P1 + status: open or module: checkout, without having to read everything.

6.The 5 commands in detail

6.1 /reversa-bug, the registrar

  1. Interviews the user about the error (what was expected, what happened, how to reproduce), following the standard Reversa menu pattern.
  2. Searches for duplicates among existing bugs; if found, offers to update the existing bug instead of creating another.
  3. Classifies with taxonomy.yaml (area, module, feature) and defines severity/priority with the user.
  4. Traces (Tracer role, internal): locates the spec section in _reversa_sdd/ that defines the expected behavior, the suspected code and existing tests. Without a corresponding spec, marks spec-gap.
  5. Correlates (Correlator role, internal): compares with existing bugs and proposes typed relationships (causes, blocked-by, duplicate-of, regression-of...).
  6. Records the origin (manual report, issue, CI failure, telemetry) and raises security suspicion: if there are indicators (authentication bypass, secret exposure...), marks security_suspected, restricts visibility and does not expose exploitable details in views or to external harnesses.
  7. Creates the folder bugs/BUG-<date>-<suffix>-slug/ with the bug.md (status: open) and evidence in evidence/ inside it.
  8. Updates the views (index, matrix, graph) and does not fix anything.
End of execution example:

  BUG-007 (BUG-20260715-A7K3) registered in _reversa_bugs/bugs/BUG-20260715-A7K3-desconto-duplicado/
  Linked spec: domain.md#regras-de-desconto
  Proposed relationship (proposed): related-to BUG-003 (rounding in the same module)

  Type CONTINUE to proceed with /reversa-bug-fix BUG-007,
  or register another bug with /reversa-bug.
  (Commands accept the canonical ID or the human number.)

6.2 /reversa-bug-fix, the lifecycle orchestrator

This is the command that takes the defect from triage to proven closure. Not every project goes through all stages: the closure policy and context define the path (a simple local bug goes straight; a production incident goes through mitigation and observation).

  1. Called with an ID (/reversa-bug-fix BUG-007). Without an ID, calculates the impact score and suggests which to fix (Prioritizer role, internal).
  2. Mitigation before investigation, when the damage is ongoing (high severity in a live system): offers via menu to reduce the damage first (disable the feature, rollback, workaround), records in mitigation: and distinguishes MITIGATED from FIXED. The bug remains active even with the service restored.
  3. Sets status: active and reproduces the defect, recording the reproduction capsule in evidence/ (base commit, environment, executed command, reproduction rate). Intermittent bugs are first-class citizens: if not reproduced, the flow can conclude with resolution_kind: instrumentation-required (adding logging, metrics or tracing to capture the next occurrence is a valid fix).
  4. Investigates the root cause with epistemological state: hypothesis, causal path and evidence, with state hypothesized → supported → confirmed. A hypothesis never enters the graph as fact. For regressions with known good and bad commits, uses git bisect formally and links the bug to the culprit commit.
  5. Evaluates the change risk (change_risk: low/medium/high, with reasons: blast radius, external contract, data, concurrency). Bug impact and fix risk are different things, and together they define the policy: low risk + confirmed cause proceeds directly; diagnostic uncertainty or high risk triggers the debate.
  6. Presents the strategy menu (box below): direct fix or multi-agent debate (diagnosis or repair mode, section 6.3).
  7. Gate 1, the test: creates the reproduction test (proves the reported defect appears) and the regression test(s) (protect what must not break again; these are distinct things). Shows the test diff, waits for approval, applies and demonstrates they fail.
  8. Gate 2, the change set: assembles the Correction Change Set, the typed set of corrective changes (code, config, migration, data repair, spec...), because not every bug is resolved with a code patch. Shows all diffs, waits for approval, applies and demonstrates the tests pass.
  9. Evaluates the data impact: fixed code does not fix corrupted historical state (code healed ≠ system healed). If there are incorrect old records, data repair enters the change set with dry-run and rollback.
  10. Executes the spec verdict (section 8), recommending with evidence; the decision is human.
  11. Closes per the closure policy: fills the Resolution with the change set and diffs together in fix/, sets the resolution_kind and updates the views (including the BUG ↔ SPEC matrix on both sides). Local library closes here; production service stays in phase: observing until the observation window confirms non-recurrence. resolved: fixed requires confirmed cause, regression tests and spec verdict.
Step 4 menu (Reversa standard):

  I found the probable root cause in src/checkout/fechamento.py:42.
  How do you want to decide the fix strategy?

  [1] Direct fix
      I proceed with my hypothesis: remove the coupon reapplication in
      aplicar_ajustes(). Faster.
  [2] Multi-agent debate
      I open a debate with N agents for R rounds + 1 judge to compare
      strategies. Note: takes longer and costs more, because it calls
      N x R sub-agents (default 3 x 2 = 6 calls + judge).
      I detected Codex CLI installed: if you accept, it can join
      as an external debater.
  [3] Other
      Describe how you prefer to decide.

6.3 /reversa-bug-debate, the discussion table

Vendor-in of the multi-agent debate loop (fixed epochs), adapted to the bug context, with three modes:

ModeWhenWhat the debaters dispute
diagnosisMultiple competing causal hypotheses.Which hypothesis the evidence supports and which probes discriminate between them.
repairConfirmed cause, competing fix strategies.Smallest coherent change, lowest regression risk, best reversibility.
specCode, tests and spec diverge and it's unclear which governs.Observed behavior vs effective spec vs contracts; ends in recommendation, the spec decision is always human.
  • Inputs locked at the start: N agents (default 3), R rounds (default 2) and problem P (the fix strategy for BUG-XXX, assembled from the bug file + root cause + linked spec).
  • Epoch 0: each debater produces their fix proposal independently, without seeing the others.
  • Rounds 1..R: synchronous update by snapshot: each debater reads ALL other proposals from the previous round, critiques and rewrites their own. No one reads updates mid-round.
  • Isolated judge: at the end of round R, a judge who did not participate in the debate and does not see the reasoning history (only the N final proposals) applies a frozen rubric (fixes the root cause? smallest coherent change? regression risk? respects the spec and Agent Notes?) and synthesizes the winning strategy in resposta-final.md.
  • Cost disclosed upfront: the command shows the estimate (N x R calls + 1 judge) and the time warning, and only runs with acceptance.
  • Multi-harness: if it detects other installed CLI harnesses (Codex, Gemini CLI, OpenCode), announces they can occupy debater seats or provide evaluation, and only uses them with acceptance or explicit request. External debaters are called in non-interactive mode and their response is recorded in the same file format as the others.
  • Multi-engine fallback: in harnesses without sub-agents, the N debaters are executed sequentially by the agent itself, maintaining the snapshot protocol.
On-disk state (auditable afterward), inside the bug's own folder:

_reversa_bugs/bugs/BUG-20260715-A7K3-desconto-duplicado/debate/
├── problema.md          P, N, R locked + judge rubric
├── rodada-0/agente-1.md ... agente-3.md
├── rodada-1/agente-1.md ... agente-3.md
├── rodada-2/agente-1.md ... agente-3.md   (agente-2 can be Codex, if accepted)
├── convergencia.md      how close the proposals got per round
└── resposta-final.md    judge synthesis, consumed by /reversa-bug-fix

6.4 /reversa-depth-inspection, the deep inspection

For when a feature "keeps having problems" and the user wants a deep scan, not a point bug.

  1. User indicates the feature (e.g.: "checkout"). The agent builds the feature map: spec sections, code files, tests and involved data.
  2. Fires specialized lenses, as parallel sub-agents when the harness supports it, otherwise in sequence:
LensWhat it looks for
Spec conformanceDivergences between implemented behavior and what the extraction says should happen.
Data flowValues that originate, transform and persist incorrectly (nulls, rounding, encoding, timezone).
Contracts and integrationsExternal calls, APIs and queues with violated contracts or missing failure handling.
Error states and edge casesUnhappy paths: empty inputs, concurrency, limits, permissions.
Test coverageSpec rules without a corresponding test; tests that pass but prove nothing.
Historical regressiongit log of the area: fixes that reverted, recurring hotfixes, files that concentrate changes.
  1. Each finding goes through dedupe against existing bugs and, if confirmed, becomes a BUG-XXX.md registered by the /reversa-bug protocol, with severity, traceability and relationships.
  2. Consolidated report in _reversa_bugs/inspections/checkout/report.md: feature map, findings per lens, created bugs, suspicious clusters.
  3. Does not fix anything. Final handoff suggests /reversa-bug-fix starting with the highest-impact bug.

The graph enables reading clusters: four distinct bugs converging on the same component indicate a common structural cause, and the agent starts recommending "fix BUG-012 first, the other three will probably fall along with it." This feeds the no-argument mode of /reversa-bug-fix.

7.Traceability in 3 dimensions

VERTICAL    SPEC ↔ CODE ↔ TEST ↔ BUG      (the square that closes a bug)
HORIZONTAL  BUG ↔ BUG                     (typed relationships: causes, blocks, duplicate-of, regression-of...)
TEMPORAL    BUG → FIX → REGRESSION        (what was fixed must remain true)

           ┌──────── SPEC ────────┐
           │                      │
          CODE                   BUG
           │                      │
           └──────── TEST ────────┘

SPEC defines. Code implements. Bug denounces the divergence.
Test proves the divergence was eliminated.

The vertical dimension is materialized in the BUG ↔ SPEC matrix from section 6.6, maintained on both sides (_reversa_bugs/spec-matrix.md and _reversa_sdd/bugs.md). Hard rule in the registry's README.md: a bug CANNOT be marked resolved with traceability.specs, root_cause_code or regression_tests empty. If no spec exists for the behavior, the bug carries spec-gap and the gap must be addressed before resolution.

The temporal dimension connects with what Reversa already has: bug regression tests can be watched with the same spirit as regression-watch.md from the forward cycle, and the future re-extraction (/reversa) sees the spec addenda generated by fixes.

8.Spec verdict: mapped and versioned fixes, with diffs together

Specific request from Sandeco: every fix must check whether the original spec of the buggy code should be versioned and changed, and the diffs go together. At the end of each fix the agent answers: "what was wrong, the code or the spec?"

VerdictMeaningAction on the spec
spec-correctThe spec described the correct behavior; the code diverged.None. The fix realigns the code to the spec.
spec-outdatedThe correct behavior changed or the spec described it wrong.Generates a versioned addendum in _reversa_sdd/addenda/ with the spec diff (excerpt before / excerpt as it should be read now). The original spec is never edited (non-destructive, same pattern as /reversa-sync).
spec-gapNo spec existed for the behavior.Generates an addendum that specifies the behavior for the first time, linked to the bug.

Effect on the Reversa cycle
The next re-extraction (/reversa) finds the addenda and marks them as superseded when regenerating the specs, exactly as already happens with /reversa-sync addenda. The extraction remains untouched between re-extractions, but whoever reads it sees the system as it is today.

12.Codex assessment (second opinion)

The design above was submitted to Codex (GPT-5, session 019f66ee), which read the original conversation, the Reversa skills pattern and the installer. General verdict: "the conceptual architecture is strong, especially in the separation between registering, diagnosing, deciding and fixing", but "slightly over-engineered in advanced capabilities and under-engineered in the basic invariants of the registry." The full assessment is in the session log; below, the essentials per question.

12.1 Identified risks and gaps

  • Formal front matter schema, with schema_version: without required fields, types and enums defined, 5 skills across multiple engines will produce incompatible variations.
  • Folder vs front matter authority: if the file is in active/ with status: open, the regenerator must stop with an explicit error, never silently fix it.
  • Canonical relationships: record the edge only once (caused-by, blocked-by, duplicate-of, regression-of) and derive the inverses (causes, blocks) in the views. Prohibit self-reference, nonexistent reference and duplicate-of cycles.
  • resolution_kind: the rule "only resolve with root cause + regression test" applies to fixed, but doesn't cover duplicate, invalid, cannot-reproduce and spec-only. Without this, legitimate bugs remain eternally open or get artificial traceability.
  • Two approval gates in the fix: the regression test also modifies the project. Gate 1: test diff, approve, apply, prove it fails. Gate 2: fix diff (+ addendum), approve, apply, prove it passes.
  • Central ID registrar: in parallel inspection, no lens creates BUG-XXX directly; lenses produce findings, a single registrar deduplicates and assigns IDs serially. This also answers the numbering collision question from section 11.
  • Effective spec: every analysis considers original spec + current addenda, never just the original.
  • No fixed paths: resolve output_folder via .reversa/state.json, don't assume _reversa_sdd/.
  • Debate is not the default path: offer primarily when there are competing causes, high risk, cross-cutting change or spec disagreement. Impact score is a triage heuristic, not mathematical truth.

12.2 Status ontology: 3 is better than 4

Codex confirms the 3 statuses: blocking is a condition orthogonal to the stage (a bug can be open and blocked by a human decision). But recommends structuring blocking beyond bug-to-bug:

blocking:
  - kind: bug
    target: BUG-031
  - kind: external
    reason: "Awaiting vendor credentials"
    since: 2026-07-15

is_blocked becomes derived, never a fourth status. This resolves the first open point from section 11.

12.3 Spec verdict: addendum is the right path, with 4 adjustments

  • Addendum as overlay: the "effective spec" is the base plus current addenda, not a new physical version of the file.
  • Human approval of the verdict: a spec extracted from legacy may faithfully describe incorrect behavior. The agent recommends the verdict with evidence, the user makes the final call.
  • Distinguish alteration from creation: spec-outdated generates an addendum with a delta of an existing section; spec-gap generates an additive overlay with a new requirement, without pretending to alter a nonexistent section.
  • Version the event: one immutable file per approved decision (e.g.: bug-BUG-042-v001.md) with target, effective date, evidence and approval, instead of rewriting a previous addendum.

Important warning: Reversa's re-extraction currently marks all addenda as superseded. For bug addenda (especially spec-gap), this should only happen after verifying that the new extraction absorbed the behavior. In the Resolution, keep code and spec united transactionally, but with summary + hash + link to the complete diff in evidence/, without pasting huge diffs into the Markdown.

12.4 External debaters: hardened protocol

  • Probe before offering: detecting the executable is not enough; probe non-interactive mode, authentication and read-only capability. Without verifiable read-only, the external CLI only evaluates provided material, never receives mutable access to the project.
  • Standardized file per debater and round: front matter with protocol_version, engine, model, round, snapshot hash, status and duration; body with fixed sections (hypotheses, root cause, strategy, test, spec impact, risks, confidence).
  • Protected judge: receives the anonymized final solutions, in shuffled order, treated as untrusted data (defense against prompt injection and against favoring an engine by name).
  • Failures: hard timeout (default 10 min), one retry only for transport failure, minimum quorum of max(2, ceil(2N/3)) to continue automatically; without quorum, menu for the user. A failing debater generates a file with status: timeout|error, never silently replaced. If the judge fails, preserve everything and don't invent a winner.
  • Roles: distinguish solver (proposes and competes) from critic (only evaluates). The cost warning shows the real bill: solvers x rounds + critics x rounds + judge.

12.5 Deep inspection: 6 lenses, with one promotion and one new

  • The 6 lenses make sense; demote "historical regression via git" from confirmatory lens to auxiliary source (shallow history does not prove absence of defect).
  • New mandatory lens: concurrency and temporal consistency (transactions, idempotency, retries, race conditions, cache, event ordering).
  • Conditional lenses, activated by signals: security/authorization, performance, configuration/migrations/flags, observability.
  • "Confirmed finding" criterion: observable deviation between expected and actual, or static proof with complete causal path. Technical debt and suspicion remain in the report as findings, with finding_id, confidence and promoted_to, without automatically becoming bugs.

12.6 Scale (200+ bugs)

  • Generate a derived compact catalog (catalog.jsonl, normalized front matter only) and do two-stage retrieval: filter the catalog, read the body only for the 10-20 candidates.
  • Global NxN matrix does not scale (200x200 = 40,000 empty cells): convert to sparse edge list and matrices filtered by cluster/status. Graph shows clusters and highest impacts, with sub-graphs per component.
  • Views with generated_at, schema version and input digest; deterministic generation, without delegating the assembly of 200 records to the LLM context.
  • Impact score calculated only on canonical edges, with limited weight for related-to; references between bugs always by ID (views resolve the current folder path).

12.7 Second round: assessment of the single folder per bug and the BUG ↔ SPEC matrix

After Sandeco's decision to concentrate everything about a bug in a single folder, Codex was consulted again (session 019f6716). Summary:

  • Flat folder, firm recommendation: _reversa_bugs/BUG-007/ with immutable physical address and status only in the front matter. Moving the folder between open/active/resolved breaks external links on every transition, generates rename/rename conflict between git branches and forces tools to search for the ID in three places. "The organization by state is a projection, not part of the bug's identity." If Sandeco prefers to keep the moves, mandatory mitigations: references only by ID, relative internal links, the registrar resolves ID → current path, validation rejects duplicate IDs and folder vs status divergence, and the folder name carries only the ID (slug stays in YAML).
  • Spec-side mirror: correct idea, as long as it is explicitly a generated view, never another source of truth. Recommended address: _reversa_sdd/traceability/bugs.md, alongside the traceability/code-spec-matrix.md that extraction already produces. Header "GENERATED, DO NOT EDIT", one section per spec, links resolved by ID. Don't create one file per spec (would multiply derived artifacts and look like altering the original spec) and don't leave the link only on the bug side (the mirror improves discoverability for those navigating the specs). Addenda remain the only authored documents that supplement the original contract.
  • Previous recommendations remain and one becomes more important: with self-contained bugs, the central ID registrar must be append-only and validation needs to catch duplicates on merge (sequential counter alone doesn't prevent collision between branches). catalog.jsonl now includes the calculated path of each bug; resolution_kind should indicate when a spec addendum was created; the two approval gates remain unchanged.

Codex synthesis for the new structure: "self-contained bug, immutable physical address, state in YAML and all matrices and catalogs as regenerable projections."

Recommendation
Fully adopt both rounds. No Codex recommendation contradicts Sandeco's locked decisions; all harden the design (versioned schema, resolution_kind, structured blocking, two gates in the fix, human approval of the spec verdict, central ID registrar, external debater protocol with quorum, concurrency lens, sparse views with catalog, mirror in _reversa_sdd/traceability/bugs.md). If approved, all of this enters the spec specs/reversa-bugs/ before implementation. 13.Daily practice assessment: triage and what changes

The third assessment (parecer_reversa_bugs_pratica_diaria_para_claude.md) brought the most structural critique: the design modeled well "agent fixes code", but not the complete defect lifecycle (intake → triage → mitigate → reproduce → diagnose → fix → deliver → observe → close). The central thesis was adopted as the project's guiding principle:

Reversa Bugs thesis
The system maintains a verifiable causal memory of the defect, repository-native, and uses specialized agents as ephemeral workers to investigate, decide, fix and prove the software's recovery. The agents are not the architecture; the architecture is state, evidence, policies and traceability.

13.1 Adopted in full

  • Folder is not a source of state + phase separate from status (§14), converging with Codex. Final structure in section 4, with single folder per bug preserved (the assessment's proposal to return to global evidence/ and debates/ folders was rejected for contradicting Sandeco's decision).
  • Reproduction test ≠ regression test (§7).
  • Epistemological state in root cause and BUG↔BUG relationships (§8, §9): hypothesized/supported/confirmed/rejected, with evidence; proposed relationship does not alter automatic prioritization.
  • Merge-safe IDs (§13): BUG-<date>-<suffix> + display_number.
  • Debate with 3 modes (§10): diagnosis, repair, spec; spec mode ends in recommendation, human decision.
  • Correction Change Set (§4): typed corrective changes; a bug does not necessarily produce a code patch.
  • code healed ≠ system healed (§5): data impact and historical state repair enter the change set.
  • Mitigation separate from fix (§3): offered via menu when the damage is ongoing; MITIGATED ≠ FIXED ≠ RESOLVED.
  • Intermittent bugs + instrumentation-required (§18) and formal git bisect (§19).
  • Security flow (§23): visibility field, no exploitable detail in views or sent to external harnesses without approval.
  • Keep the 5 commands (§28): the gain enters the state machine and schemas, not in new commands.

13.2 Adopted simplified (lean v1)

  • Closure policy by project profile (§2, §16): 3 profiles detected on first run (local-software, package, production-service), defining what "resolved" requires. Phases reduced to the useful core.
  • Reproduction capsule (§6): essential version (base commit, environment, command, rate), without exhaustive digests.
  • Optional blocks by context: delivery/PR/CI (§15), post-fix observation (§17), versions and backports (§20), ownership via CODEOWNERS (§21), external origin (§22). The schema supports them; the agent only fills them when the project has the resource.
  • Qualitative change_risk (§24): low/medium/high with reasons, feeding the strategy menu; no numeric score with appearance of precision.
  • Control modes (§25): gated default; supervised and autonomous available. Even in autonomous, spec, security and destructive operations keep the gate.
  • Stable spec IDs (§11): starts with ID + locator resolved by views; full catalog deferred until re-extraction proves the need.

13.3 Deliberately deferred

  • Postmortem policy (§26): conversation with the future maintenance team (SRE/DORA) already drafted in specs/time-de-manutencao/.
  • Deep integrations with GitHub/GitLab/Sentry: the schema records references, but no active integration in v1.
  • Numeric confidences (0.94): replaced by qualitative levels.

13.4 Acceptance bar

The 10 scenarios from the assessment (§30) become spec acceptance criteria: simple local bug closes without bureaucracy; production incident doesn't close with local test; data corruption distinguishes healed code from healed system; intermittent allows instrumentation without inventing a cause; regression links bug to culprit commit via bisect; multiple versions respect pending backport; spec divergence requires human decision; vulnerability doesn't leak in views; two harnesses in worktrees don't collide IDs; high-risk fix considers change_risk.
